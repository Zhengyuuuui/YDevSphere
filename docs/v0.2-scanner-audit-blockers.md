## 一、阻塞项（必须重做）

### 🔴-1 聚合根子项目入库语义与「父项目边界优先」规则矛盾

**问题**：`core/scanner/mod.rs` 的 `classify_dir` 在判定聚合根后，把 frontend/backend/bridge 等子项目**作为独立 `DetectedProject` 入库**（注释自称「仍需识别入库」）。这与 plan §2.1 的关键规则冲突：

> 「一旦 D 判定为『真项目』或『聚合根』，**其后代一律不生成卡片**，只作 D 的 tree 子结构。」

当前实现下，`get_projects`（默认 `parent_id_filter = None`）会把聚合根与其子项目**并列返回**，导致 `sub2api`、`frontend`、`backend`、`bridge` 变成 4 张卡片，与验收标准六·2（sub2api 一张卡片，子项目作 tree 子结构）不一致。

**需后端 agent 明确并实现交付形态（二选一，建议与总负责人确认）**：

- **方案 A（推荐，改动小）**：子项目仍入库（保留 `parent_id` 归属），但前端默认只渲染顶层卡片——后端需保证 `get_projects` 默认语义明确（例如默认仅返回 `parent_id IS NULL` 的顶层项目，子项目经 `parent_id_filter` 或 `get_dir_children` 按需获取），并同步前端渲染约定。
- **方案 B**：聚合根子项目**不落库为项目行**，仅作 tree 数据（经 `get_dir_children` 实时读取），后端 `classify_dir` 对聚合根后代停止递归、不 `push` 子项目。

无论选哪种，都需：
1. 用注释/文档明确「聚合根后代不生成卡片」的落地方式。
2. 补充或修正对应单测，覆盖「聚合根 + 子项目」场景下的**顶层卡片数量**与**子项目获取路径**。

## 二、关联警告（与阻塞项同批处理）

### 🟡-1 同步清理缺少聚合根父子级联单测

`database/crud.rs` 的 `delete_missing_projects` 仅覆盖「顶层 + 独立项目」单测，未覆盖「删除聚合根下某个子目录 / 整个聚合根目录」场景。需补单测验证：
- 删除聚合根整个目录 → 父 + 子项目均被清理；
- 仅删除聚合根下某个子目录 → 父保留、对应子项目被清理。

### 🟡-2 健康度「清单 +20」依赖 `kind` 而非实际清单存在

`scanner/mod.rs` `health_score` 中 `if kind == ProjectKind::Real && has_manifest(dir)` 才 +20。建议改为 `if has_manifest(dir) { score += 20 }`，使加分维度与 plan §2.3「含清单文件 +20」字面一致，消除隐式约定耦合。
